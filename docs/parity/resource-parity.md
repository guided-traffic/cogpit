# Resource parity: views, columns and actions

> **Target:** Lens Desktop 2026.10.51501

Every Kubernetes resource view Lens Desktop has, with the columns of its list and the actions it
offers, against Cogpit. The layout around these views (sidebar, tables, detail drawer, dock) is in
[`ui-parity.md`](ui-parity.md); method and status vocabulary in [`README.md`](README.md).

**Sources.** Lens Desktop's documentation, one page per view under
[Using Lens](https://docs.lenshq.io/k8slens/using-lens/layout/) (Workloads, Config, Network,
Storage, Device Resources, Namespaces, Events, Helm, Access Control, Applications, Nodes,
Overview), its release notes to 2026.10.51501, and captures of the running Lens Desktop where a row
says *captured*. *Capture needed* marks what the documentation leaves open, *inferred* Cogpit's
own choice where no source shows Lens's behaviour
([D-12](../developer/decisions.md#d-12-parity-sources)).

All views and actions on this page are in Lens Desktop's free plan, except the section
[Paid Lens Desktop views](#paid-lens-desktop-views). **Command ids** are Cogpit's, following
[conventions](../developer/conventions.md#style); they are the registry ids and, with underscores,
the MCP tool names.

**Summary (measured by `make parity`):** 64 of 64 resource views exist: one done (the custom
resource views) and 63 partial, ten of them the Gateway API views, which show as generic custom
resource views until their columns are captured. 42 of 42 actions exist, all partial; missing:
none. Most texts and rules of the partial views are inferred, not checked against a running Lens,
and the actions are limited as each row notes. Counted from the rows below (the two Gateway API
rows hold seven and three views; Share is not a target). Lens Desktop's paid features add 24 views
and 3 actions. Remaining (estimated, 2–6 h per view or action with tests): 30–100 h for the views
([G6](gaps.md#g6-resource-views)) and 20–70 h for the actions
([G7](gaps.md#g7-resource-actions)), on top of the foundation in [G1–G4](gaps.md#summary).

Evidence for the view rows: the kind profiles in
[`internal/model/kinds`](../../internal/model/kinds/) with their golden tests (`TestGolden`,
`TestStatusTexts`, `TestBuiltinProfiles`), the engine's views, and the views filled from watches on
kind (`TestKindEngineWorkflows`). The actions also run against a real cluster
([D-62](../developer/decisions.md#d-62-checks-against-a-real-cluster)): `TestRealWorkloadActions`,
`TestRealNodeCordon`, `TestRealNodeDrain`, `TestRealNodeShell`, `TestRealHelm`, `TestRealFlux`.

## Create dialogs

Lens Desktop has dialogs (not YAML) to create Namespaces, Secrets, Resource Quotas, Service
Accounts, Cluster Roles, Roles, Cluster Role Bindings and Role Bindings; their command ids are in
the tables above. Everything else is created from YAML templates in the dock
([ui-parity › Editor](ui-parity.md#editor-and-create-resource)).

All eight are built. None of Lens's dialogs is captured: the fields, their order and where a dialog
opens (the view's "+") are inferred from Lens's documentation of the views; layout and texts are
Cogpit's. Each dialog dispatches an engine command, which is also an MCP tool
([`commands/createdialogs.go`](../../internal/engine/commands/createdialogs.go),
[`engine/createdialogs.go`](../../internal/engine/createdialogs.go),
[`createdialog.go`](../../internal/ui/fyneui/createdialog.go); the Secret's in
[`commands/secretcreate.go`](../../internal/engine/commands/secretcreate.go) and
[`createdialog_secret.go`](../../internal/ui/fyneui/createdialog_secret.go)). The Secret's is the
user's alone ([D-19](../developer/decisions.md#d-19-editing-and-creating-secrets-from-yaml)): its
command refuses agents and the CLI before anything is asked or sent.

**Every dialog** (`TestCreateDialogsDryRunThenCreate`, `TestCreateButtonOpensTheKindsDialog`): the
namespace starts as the namespace filter's single namespace, else the context's default
(`TestCreateDialogsNamespaceDefault`); Create sends the command, which checks the fields
(`TestCreateDialogsCheckTheirParameters`), runs a server-side dry run and then the create, as a
Create resource tab does (`TestCreateDialogRefusedByTheDryRun`); an error keeps the dialog open
with the reason (`TestCreateDialogStaysOpenOnError`); Create is greyed with the access reviews'
reason when they deny `create` in the chosen namespace (`TestCreateDialogsFollowAccessReviews`,
`TestCreateDialogNotPermitted`); names are offered from the cache (`resources.list`), never listed
by the dialog itself (`TestRoleBindingDialogOffersTheCache`). After the user's create of one
object, its drawer opens and the list scrolls to its row (`TestCreateShowsTheNewObject`; what Lens
does then is not captured). On kind: `TestKindCreateDialogs` (one object of each kind, the bindings
checked with SubjectAccessReviews, a quota on an unknown resource refused by the dry run).

**Danger.** Every create is mutating, so an agent's waits for the user's acceptance
([D-2](../developer/decisions.md#d-2-agent-interface-scope)), which names the rules, the limits, or
the role and subjects a binding grants. An agent's create or change of a Role, Cluster Role, Role
Binding or Cluster Role Binding, from a dialog or from YAML, always waits for the user, also where
the user allowed agent writes for the context (`TestAgentRoleBindingsAlwaysAsk`,
`TestTextHoldsRBAC`). Two creates are confirmed for every origin, the GUI too: a Cluster Role
Binding (registered destructive: a grant in every namespace and on cluster-scoped resources) and a
Role Binding to `cluster-admin` or to a role Cogpit's cache holds whose rules allow every verb on
every resource (escalated to destructive) (`TestCreateDialogsAgentsNeedAcceptance`,
`TestRoleBindingToAWildcardRoleEscalates`). A binding's confirmation has the rows Grants, To and
Takes effect ("immediately, cluster-wide" in the warning colour, or "immediately, in namespace
<ns>"); "This cannot be undone." appears only on confirmations where something is lost (delete,
drain, uninstall), not on a grant's. Roles grant nothing until bound and stay mutating; the API
server's escalation check refuses a role or binding that grants more than the user holds. Why and
what remains: [privilege footprint](../security/privilege-footprint.md#actions-that-write),
[H-27](../security/privilege-footprint.md#h-27-a-binding-is-judged-by-its-roles-name-and-the-cache).

Not built: labels and annotations in the seven dialogs other than the Secret's; a cluster role's
aggregation rule; resource names in the GUI's rule rows (agents can give them); a quota's scopes
and scope selector.
